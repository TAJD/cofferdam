# Cut a cofferdam release

## Overview

Cofferdam's version number lives in **six** places. Any one of them being out of sync breaks something downstream — npm publishes the wrong tag, `cofferdam --version` lies, or `release.yml` fails the integrity check. The release process is mechanical but easy to miss one. This skill encodes the full sequence.

The actual GitHub Release + npm publish + binary upload is automated by `.github/workflows/release.yml`, triggered by pushing a `vX.Y.Z` tag. **Don't** publish manually.

## When to use

- "release 0.3.2" / "cut a release" / "tag vX.Y.Z"
- "bump cofferdam to 0.4.0"
- "publish a patch / minor / major"
- After landing a fix the user wants to ship

**Do NOT use** for: pre-release tagging strategies, yanking a published version, hotfixing a tag that's already cut. Those need bespoke handling.

## Pre-flight

Refuse to proceed if any of these fails:

```bash
git rev-parse --abbrev-ref HEAD          # must be main
git status --porcelain                   # must be empty
git log @{u}..HEAD --oneline             # must be empty (in sync with origin)
gh run list --branch main --limit 3 --json conclusion,name  # latest `ci` must be success
```

If `ci` is failing or queued, stop and report. Don't release on red.

## Use the deterministic script — `scripts/version.mjs`

**Don't hand-edit the version locations.** As of cd-9hp.2 there is one
self-contained tool (Node, no `cargo-edit` dependency) that owns all of
them:

```bash
node scripts/version.mjs check          # assert every location agrees (internal consistency)
node scripts/version.mjs check 0.3.4    # ...and that they all equal this version (CI passes the tag)
node scripts/version.mjs set 0.3.4 --regen   # rewrite every location + regen Cargo.lock + checks.json
```

`release.yml`'s `verify` job runs `version.mjs check <tag>` before the
build matrix, so a forgotten bump now **fails the release loudly**
instead of shipping a tag that disagrees with the repo (the v0.3.3
botch). The manual sequence below is the fallback / explanation of what
the script does — prefer the script.

## Where the version lives (derived, not a fixed list)

| File | Form |
|------|------|
| `Cargo.toml` (workspace.package) | `version = "X.Y.Z"` |
| `Cargo.toml` (workspace.dependencies) | `cofferdam-{core,engine,checks,formatters,graph,rust} = { ..., version = "X.Y.Z" }` |
| **any member crate `Cargo.toml`** | direct `cofferdam-* = { path = "...", version = "X.Y.Z" }` pins — e.g. `crates/cofferdam-cli/Cargo.toml` pins `cofferdam-lsp` (NOT in `[workspace.dependencies]`) |
| `packages/check-sdk/package.json` | `"version": "X.Y.Z"` |
| `packages/cofferdam/package.json` | `"version": "X.Y.Z"` |
| `Cargo.lock` | regenerated by `cargo build` |
| `docs/public/checks.json` | regenerated by `cofferdam gen-docs` (top-level `cofferdam_version` field) |

> **The list of pins is derived, not fixed — `version.mjs` scans every
> `Cargo.toml`, not just the root.** The old "six places" framing missed
> the `cofferdam-cli` → `cofferdam-lsp` pin (lsp isn't a
> `[workspace.dependencies]` entry, so a root-only `git grep` skipped it)
> and it had silently drifted. To audit by hand:
> ```bash
> git grep -nE 'cofferdam-[a-z]+ = \{ path' -- '**/Cargo.toml' 'Cargo.toml'
> ```
> Crates not depended on internally (`cli`, `napi`) have no pin — they
> inherit the workspace version, so the `workspace.package` bump covers
> them.
>
> **Deliberately OUT of lockstep:** `editors/vscode/package.json`. The VS
> Code extension is a stub published by no workflow; it versions
> independently. `version.mjs` ignores it by design. If it ever joins
> the release, add it to the script.

> **The in-repo version files do NOT gate the npm publish — the git tag does.** `release.yml` derives the published version from the `vX.Y.Z` tag, so it is entirely possible to tag + publish a new version while every file above still says the *old* version, and nothing fails loudly — `cofferdam --version` just quietly lies. This actually happened: **v0.3.3 shipped to npm with all repo files still at 0.3.2.** Run the drift check below at the *start* (not just before step 4) to confirm the in-repo version matches the last published one before you decide the bump.

## Sequence

1. **Decide the bump.** First confirm the repo isn't already drifted from the last release (see the npm-vs-tag warning above):
   ```bash
   git describe --tags --abbrev=0                        # last tag, e.g. v0.3.3
   git grep -nE '^version = ' Cargo.toml | head -1       # in-repo version
   npm view @cofferdam/cofferdam version                 # published version
   ```
   If the in-repo version is *behind* the published one, the previous release botched its bump — your new version must move forward past the published one (e.g. published 0.3.3 + repo 0.3.2 → next is **0.3.4**, never re-tag 0.3.3). Then read commits since the last tag and apply semver:
   ```bash
   git log --oneline $(git describe --tags --abbrev=0)..HEAD
   ```
   Patch for bug fixes; minor for new checks/features; major for breaking config or ID changes.

2. **Bump every version location + regenerate artefacts** in one step:
   ```bash
   node scripts/version.mjs set X.Y.Z --regen
   ```
   This rewrites `Cargo.toml` (workspace version + all `cofferdam-*` path-dep pins across every crate), both `package.json` files, then runs `cargo build --workspace` (Cargo.lock) and `cofferdam gen-docs` (checks.json). `gen-docs` is the historically **most-forgotten step** — `--regen` removes the chance to forget it. If you bump by hand instead, the script's `check` (step 5) catches anything you missed.

3. **Update `CHANGELOG.md`.** Move entries from `[Unreleased]` into a new `## [X.Y.Z] - YYYY-MM-DD` section above the previous release. Use today's date in ISO format. Group entries under `### Added` / `### Changed` / `### Fixed` / `### Removed` / `### Deprecated` / `### Security` per Keep a Changelog. Each bullet should reference the bead id and gh issue number when one exists.

4. *(Folded into step 2's `--regen`.)* If you ran `set` without `--regen`, regenerate now: `cargo build --workspace` then `cargo run -p cofferdam-cli -- gen-docs`.

5. **Verification block.** All must pass:
   ```bash
   node scripts/version.mjs check X.Y.Z        # every version location agrees + equals X.Y.Z
   ```
   then:
   ```bash
   cargo fmt --all -- --check
   cargo clippy --workspace --all-targets -- -D warnings
   cargo test --workspace
   cargo run -p cofferdam-cli --quiet -- gen-docs --check
   ```

6. **Commit.** Use a HEREDOC, follow prior format (`git log --oneline | grep release:`):
   ```bash
   git add CHANGELOG.md Cargo.lock Cargo.toml docs/public/checks.json \
           packages/check-sdk/package.json packages/cofferdam/package.json
   git commit -m "$(cat <<'EOF'
   release: vX.Y.Z

   <patch|minor|major>: <one-line summary of the bucket>

   - <bead-id> / gh #<n>: <one-line per shipped change>
   - ...

   See CHANGELOG.md for details.

   Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
   EOF
   )"
   ```

7. **Tag and push.** Annotated tag (release.yml expects this):
   ```bash
   git tag -a vX.Y.Z -m "vX.Y.Z — <one-line summary>"
   git push origin main
   git push origin vX.Y.Z
   ```
   Pushing the tag triggers `.github/workflows/release.yml`. Do **not** run `npm publish` or `cargo publish` manually.

8. **Verify the release pipeline started:**
   ```bash
   gh run list --limit 5 --json status,name,headSha
   ```
   The `release` workflow should be queued or running on the new tag's SHA. Don't poll — it takes several minutes (binary builds across the matrix).

## Quick reference

```bash
# Drift check — run BEFORE step 4 to confirm step 2 was complete
git grep -nE '"OLD\.VER\.SION"|version = "OLD\.VER\.SION"' \
    -- ':!CHANGELOG.md'

# Last released tag
git describe --tags --abbrev=0

# Commits eligible for the new release
git log --oneline $(git describe --tags --abbrev=0)..HEAD
```

## Common mistakes

| Mistake | What happens | Fix |
|---|---|---|
| Forgot `cofferdam gen-docs` | CI fails on the release commit (`gen-docs --check` reports `docs/public/checks.json` out of date) | Run gen-docs, amend? **No — add a follow-up commit** (cofferdam policy: never amend pushed commits). Better: catch it in step 5. |
| Updated `Cargo.toml` version but not all `workspace.dependencies` pins (6 today, count varies) | `cargo build` warns / publish fails on path-vs-version mismatch | The grep in the Quick Reference catches this. |
| Tagged + published but forgot to bump the in-repo version files at all | npm/tag say new version, repo + `cofferdam --version` still say old — silent, no CI failure | Start-of-sequence drift check (step 1) catches the *previous* botch; the step-2 grep prevents your own. |
| Tagged before pushing the commit | `release.yml` checks out a tag whose SHA isn't on origin/main | Push commit first, then tag. |
| Used a lightweight tag (`git tag vX.Y.Z`) | release.yml's tag-message extraction breaks | Always `git tag -a vX.Y.Z -m "..."`. |
| Tried `npm publish` manually | Conflicts with the workflow's publish step; produces duplicate-version errors | Don't. The workflow handles it. |
| Released on a red `ci` run | Tag propagates a known-broken main; users hit it via `npm install -D @cofferdam/cofferdam@latest` | Pre-flight gate: confirm latest `ci` is green before step 1. |
| Cargo.lock not regenerated (skipped step 4) | Diff shows version mismatches between Cargo.toml and Cargo.lock | `cargo build --workspace` refreshes it; commit alongside the rest. |

## Real-world impact

v0.3.2 (2026-05-07): the gen-docs footgun nearly slipped through — `gen-docs --check` only reported the failure mid-verification block, not before. Without this skill, a fresh agent would likely commit / push / tag, then watch CI fail on the release commit and have to file a follow-up to fix it. The grep-for-old-version pattern caught a similar near-miss when the `workspace.dependencies` pins existed only in this codebase's recent history (older releases bumped them by hand).

v0.3.3 (2026-05-20): shipped to npm under the `v0.3.3` tag **without bumping a single in-repo version file** — `Cargo.toml`, all internal pins, and both `package.json` files stayed at 0.3.2. Because `release.yml` reads the version from the tag, nothing failed; the breakage was silent (`cofferdam --version` reported 0.3.2 while `npm install` gave 0.3.3). Discovered only when someone asked about the *next* release. Lesson encoded as the step-1 drift check and the in-repo-files-don't-gate-publish warning above.
