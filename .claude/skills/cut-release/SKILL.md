# Cut a cofferdam release

## Overview

Cofferdam's version number lives in **six** places. Any one of them being out of sync breaks something downstream — npm publishes the wrong tag, `cofferdam --version` lies, or `release.yml` fails the integrity check. The release process is mechanical but easy to miss one. This skill encodes the full sequence.

The actual GitHub Release + npm publish + binary upload is automated by `.github/workflows/release.yml`, triggered by pushing a `vX.Y.Z` tag. **Don't** publish manually.

## When to use

- "release 0.3.2" / "cut a release" / "tag vX.Y.Z"
- "bump cofferdam to 0.4.0"
- "publish a patch / minor / major"
- After landing a fix the user wants to ship

**Do NOT use** for: pre-release tagging strategies, yanking a published version, hotfixing a tag that's already cut. Those need bespoke handling.

## Pre-flight

Refuse to proceed if any of these fails:

```bash
git rev-parse --abbrev-ref HEAD          # must be main
git status --porcelain                   # must be empty
git log @{u}..HEAD --oneline             # must be empty (in sync with origin)
gh run list --branch main --limit 3 --json conclusion,name  # latest `ci` must be success
```

If `ci` is failing or queued, stop and report. Don't release on red.

## The six places version lives

| File | Form |
|------|------|
| `Cargo.toml` (workspace.package) | `version = "X.Y.Z"` |
| `Cargo.toml` (workspace.dependencies, ×4 lines) | `cofferdam-{core,engine,checks,formatters} = { ..., version = "X.Y.Z" }` |
| `packages/check-sdk/package.json` | `"version": "X.Y.Z"` |
| `packages/cofferdam/package.json` | `"version": "X.Y.Z"` |
| `Cargo.lock` | regenerated by `cargo build` |
| `docs/public/checks.json` | regenerated by `cofferdam gen-docs` (top-level `cofferdam_version` field) |

## Sequence

1. **Decide the bump.** Read commits since the last tag and apply semver:
   ```bash
   git log --oneline $(git describe --tags --abbrev=0)..HEAD
   ```
   Patch for bug fixes; minor for new checks/features; major for breaking config or ID changes.

2. **Edit the human-edited files** (Cargo.toml, both package.json files). Change every occurrence of the prior version. Verify nothing leaked:
   ```bash
   git grep -nE '"OLD\.VER\.SION"|version = "OLD\.VER\.SION"'
   ```
   Output should be empty (excluding `Cargo.lock`, which step 4 regenerates, and historical entries in `CHANGELOG.md` / `.beads/issues.jsonl`).

3. **Update `CHANGELOG.md`.** Move entries from `[Unreleased]` into a new `## [X.Y.Z] - YYYY-MM-DD` section above the previous release. Use today's date in ISO format. Group entries under `### Added` / `### Changed` / `### Fixed` / `### Removed` / `### Deprecated` / `### Security` per Keep a Changelog. Each bullet should reference the bead id and gh issue number when one exists.

4. **Regenerate generated artefacts.**
   ```bash
   cargo build --workspace                              # refreshes Cargo.lock
   cargo run -p cofferdam-cli --quiet -- gen-docs       # refreshes docs/public/checks.json (carries cofferdam_version)
   ```
   `gen-docs` is the **most-forgotten step**. CI runs `gen-docs --check`; forgetting this fails CI on the release commit itself.

5. **Verification block.** All four must pass:
   ```bash
   cargo fmt --all -- --check
   cargo clippy --workspace --all-targets -- -D warnings
   cargo test --workspace
   cargo run -p cofferdam-cli --quiet -- gen-docs --check
   ```

6. **Commit.** Use a HEREDOC, follow prior format (`git log --oneline | grep release:`):
   ```bash
   git add CHANGELOG.md Cargo.lock Cargo.toml docs/public/checks.json \
           packages/check-sdk/package.json packages/cofferdam/package.json
   git commit -m "$(cat <<'EOF'
   release: vX.Y.Z

   <patch|minor|major>: <one-line summary of the bucket>

   - <bead-id> / gh #<n>: <one-line per shipped change>
   - ...

   See CHANGELOG.md for details.

   Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
   EOF
   )"
   ```

7. **Tag and push.** Annotated tag (release.yml expects this):
   ```bash
   git tag -a vX.Y.Z -m "vX.Y.Z — <one-line summary>"
   git push origin main
   git push origin vX.Y.Z
   ```
   Pushing the tag triggers `.github/workflows/release.yml`. Do **not** run `npm publish` or `cargo publish` manually.

8. **Verify the release pipeline started:**
   ```bash
   gh run list --limit 5 --json status,name,headSha
   ```
   The `release` workflow should be queued or running on the new tag's SHA. Don't poll — it takes several minutes (binary builds across the matrix).

## Quick reference

```bash
# Drift check — run BEFORE step 4 to confirm step 2 was complete
git grep -nE '"OLD\.VER\.SION"|version = "OLD\.VER\.SION"' \
    -- ':!CHANGELOG.md' ':!.beads/'

# Last released tag
git describe --tags --abbrev=0

# Commits eligible for the new release
git log --oneline $(git describe --tags --abbrev=0)..HEAD
```

## Common mistakes

| Mistake | What happens | Fix |
|---|---|---|
| Forgot `cofferdam gen-docs` | CI fails on the release commit (`gen-docs --check` reports `docs/public/checks.json` out of date) | Run gen-docs, amend? **No — add a follow-up commit** (cofferdam policy: never amend pushed commits). Better: catch it in step 5. |
| Updated `Cargo.toml` version but not the four `workspace.dependencies` pins | `cargo build` warns / publish fails on path-vs-version mismatch | The grep in the Quick Reference catches this. |
| Tagged before pushing the commit | `release.yml` checks out a tag whose SHA isn't on origin/main | Push commit first, then tag. |
| Used a lightweight tag (`git tag vX.Y.Z`) | release.yml's tag-message extraction breaks | Always `git tag -a vX.Y.Z -m "..."`. |
| Tried `npm publish` manually | Conflicts with the workflow's publish step; produces duplicate-version errors | Don't. The workflow handles it. |
| Released on a red `ci` run | Tag propagates a known-broken main; users hit it via `npm install -D @cofferdam/cofferdam@latest` | Pre-flight gate: confirm latest `ci` is green before step 1. |
| Cargo.lock not regenerated (skipped step 4) | Diff shows version mismatches between Cargo.toml and Cargo.lock | `cargo build --workspace` refreshes it; commit alongside the rest. |

## Real-world impact

v0.3.2 (2026-05-07): the gen-docs footgun nearly slipped through — `gen-docs --check` only reported the failure mid-verification block, not before. Without this skill, a fresh agent would likely commit / push / tag, then watch CI fail on the release commit and have to file a v0.3.3 to fix it. The grep-for-old-version pattern caught a similar near-miss when the four `workspace.dependencies` pins existed only in this codebase's recent history (older releases bumped them by hand).
